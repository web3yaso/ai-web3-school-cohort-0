# Week 1 Web3 任务：比较 EOA、智能账户和多签账户

## 任务目标

比较 EOA、智能账户和多签账户的权限差异，理解：

- 谁持有控制权
- 谁可以发起交易
- 谁可以批准交易
- 是否支持多人确认
- 是否支持恢复、限额或自动化策略
- 典型使用场景
- 主要风险点

核心问题是：**一个链上账户到底由谁控制，交易由谁发起，风险最终落在谁身上。**

## 一句话定义

**EOA（Externally Owned Account）**  
由私钥直接控制的钱包地址，例如 MetaMask 普通钱包。谁掌握私钥，谁就能发起交易。

**智能账户（Smart Account / Smart Contract Wallet）**  
由智能合约逻辑控制的钱包。它可以把权限、限额、恢复、批量交易、自动化策略写进合约规则里。

**多签账户（Multisig Account）**  
一种常见的智能账户，通常用 Safe。它要求多个签名人中达到一定门槛后，交易才能执行，例如 2-of-3 或 3-of-5。

## 对比表

| 维度 | EOA | 智能账户 | 多签账户 |
| --- | --- | --- | --- |
| 谁持有控制权 | 单个私钥 | 合约规则 + 授权 signer / session key / module | 多个 owner 共同控制 |
| 谁可以发起交易 | 私钥持有人 | 被合约允许的账户、服务或自动化模块 | 任意 owner 或有权限的 proposer 可发起提案 |
| 谁可以批准交易 | 私钥签名即批准 | 按合约逻辑判断，例如 owner、guardian、policy engine | 达到 threshold 的 owner 批准 |
| 是否支持多人确认 | 不原生支持 | 可以通过合约逻辑支持 | 原生核心能力 |
| 是否支持恢复 | 不原生支持，丢私钥通常就丢账户 | 可以支持社交恢复、guardian、延时恢复 | 可以通过多个 owner、替换 owner 实现恢复 |
| 是否支持限额 | 不原生支持 | 可以设置每日限额、单笔限额、白名单、session key | 可结合 Safe module / guard 实现限额 |
| 是否支持自动化策略 | 不原生支持 | 可以支持自动支付、批量交易、gas sponsorship、策略执行 | 可通过 module 支持，但通常偏治理和资金管理 |
| 典型使用场景 | 个人钱包、测试网操作、普通转账、签名登录 | 消费级钱包、游戏账户、AI agent 钱包、订阅支付、批量操作 | 团队金库、DAO treasury、项目资金管理、高价值资产托管 |
| 主要风险点 | 私钥单点失效；签错交易就直接生效 | 合约漏洞、策略配置错误、模块权限过大 | owner 串谋、threshold 设置不合理、签名人丢 key、执行流程慢 |

## 权限流对比

### EOA：私钥就是账户

EOA 的权限模型最简单：

```text
私钥持有人
  -> 签名交易
  -> 交易直接从 EOA 发出
  -> 链上状态改变
```

优点是简单、兼容性最好、学习成本低。  
缺点是控制权高度集中在一个私钥上。

如果私钥泄露，攻击者可以立刻转走资产。  
如果私钥丢失，账户通常无法恢复。  
如果用户签错授权或交易，链上结果很难撤销。

所以 EOA 适合低风险个人操作，但不适合管理团队资金或高价值资产。

## 智能账户：账户是一套规则

智能账户不是直接由一个私钥决定一切，而是由合约逻辑判断“这笔交易是否允许执行”。

```text
用户 / agent / session key
  -> 提交操作
  -> 智能账户合约检查权限规则
  -> 规则通过后执行交易
```

智能账户可以支持：

- 批量交易：把多个操作合并成一次
- session key：给某个临时 key 有限权限
- gas sponsorship：由第三方代付 gas
- 社交恢复：通过 guardian 恢复账户
- 支出限额：限制每日或单笔最大金额
- 白名单策略：只允许调用指定合约或地址
- 自动化策略：在权限范围内自动执行某些操作

智能账户的核心优势是**可编程权限**。  
它不只是“谁有私钥谁控制”，而是“合约规则允许什么，什么才可以执行”。

主要风险也来自这层复杂性：

- 合约代码可能有漏洞
- module 或 plugin 权限可能过大
- session key 范围设置错误会扩大损失
- 恢复机制如果设计不好，可能被滥用
- 用户可能看不懂合约实际会执行什么

## 多签账户：多人共同批准

多签账户是智能账户的一种典型形式。最常见的是 Safe。

例如一个 2-of-3 多签：

```text
Owner A
Owner B
Owner C

任意 2 个 owner 批准
  -> 交易可以执行
```

多签把风险从“单个私钥”拆成“多个签名人的协作”。

它适合：

- 团队 treasury
- DAO 资金管理
- 项目部署权限
- 高价值 NFT 或 token 托管
- 公司或组织的链上账户

多签并不一定要求多人。一个人也可以用多个设备做 2-of-3：

- 硬件钱包
- 手机热钱包
- 电脑钱包

这样攻击者需要同时攻破多个设备，风险比单个 EOA 更低。

多签的风险主要是治理和运营风险：

- threshold 太低，安全性不足
- threshold 太高，紧急时无法执行
- 多个 owner 丢失私钥，账户可能卡死
- owner 串谋，可以转走资金
- 签名人不认真检查交易内容，可能集体签错

## “谁能发起、谁能批准、谁承担风险”

### EOA

- 发起者：私钥持有人
- 批准者：同一个私钥持有人
- 风险承担者：账户所有者
- 风险模式：单点失效

EOA 的发起和批准几乎是同一个动作。只要钱包签名，交易就可以广播并执行。

### 智能账户

- 发起者：用户、agent、session key、relayer 或自动化模块
- 批准者：智能账户合约逻辑
- 风险承担者：账户所有者，以及设计这些权限规则的人
- 风险模式：策略错误或合约风险

智能账户把“发起交易”和“允许执行”拆开了。  
这让账户更灵活，但也要求权限设计更清晰。

### 多签账户

- 发起者：某个 owner 或 proposer
- 批准者：达到 threshold 的多个 owner
- 风险承担者：多签 owner 集体，以及 treasury 受益方
- 风险模式：协作失败、串谋、签名人失误

多签把批准权分散给多个人或多个设备。  
它牺牲了一些便利性，换来更强的安全性和责任分离。

## 典型场景判断

### 个人测试网学习

推荐：EOA

原因：简单、成本低、工具支持最好。  
注意：只放测试资产或小额资产，不要把主钱包私钥用于实验。

### 消费级 dApp 钱包

推荐：智能账户

原因：可以支持恢复、免 gas 体验、批量操作和权限控制。  
注意：要确认账户合约和 module 是否可信。

### AI agent 自动执行小额任务

推荐：智能账户或 Safe + agent signer

原因：可以给 agent 设置限额、白名单和人工确认门槛。  
注意：agent key 不能拥有无限权限，高风险操作必须人工确认。

### 团队资金管理

推荐：多签账户

原因：团队资金不应由单个私钥控制。  
注意：合理设置 threshold，例如 2-of-3、3-of-5，并保留恢复方案。

### DAO Treasury

推荐：多签账户 + 治理流程

原因：资金属于组织，需要多人批准和公开透明的执行记录。  
注意：多签 owner 需要有明确责任，不能只是“挂名签名人”。

## 我的理解

EOA 是最简单的账户模型，控制权集中在一个私钥上。它适合个人学习和低风险操作，但私钥泄露或丢失都会造成严重后果。

智能账户把账户变成一套可编程规则。它可以支持恢复、限额、自动化、批量交易和更好的用户体验，但也引入了合约和权限配置风险。

多签账户是智能账户中最常见的高安全用法。它通过多人或多设备确认降低单点私钥风险，适合团队和高价值资金管理，但需要设计好 owner、threshold 和应急流程。

最重要的区别不是地址长什么样，而是：**交易由谁提出、由谁批准、规则在哪里执行、出错后谁承担损失。**
