## Part 1：Web3 基础（4个核心模块）

### 1. Network（网络）

**核心认知：**
- 区块链网络的核心不是"存数据"，而是让互不信任的参与者对状态变化达成一致
- 链上应用不是直接写数据库，而是在公开、按区块推进、由网络共识维护的状态机上提交请求

**关键知识点：**
- **Block**：交易被批量提交和排序的单位。交易有顺序、区块有 gas limit、新区块形成可验证历史
- **Consensus（共识）**：网络决定"哪段历史有效"的机制，影响交易确认数和短暂重组风险
- **PoS（权益证明）**：验证者质押 ETH 参与区块提议和证明，行为错误可被惩罚
- **Testnet**：用于测试合约和交易流程，资产无真实价值，不能替代主网安全审查
- **L2**：在主网安全和更低成本之间做权衡，常见方案有 Optimism、Arbitrum、zkSync、Base

**一笔交易的旅程：**
钱包签名 → RPC 广播 → memool 待确认 → 区块打包 → 共识确认 → 执行 → 状态更新 → 索引 → 浏览器可见

### 2. Cryptography（密码学）

**核心认知：**
- 链上身份不由平台发放，而是由能否证明控制某个私钥决定
- 密码学不是抽象理论，而是产品边界

**关键知识点：**
- **Hash（哈希）**：把任意数据变成固定长度指纹，用于验证数据一致性。哈希不是加密，不可还原原文
- **Public Key**：和私钥成对出现，可公开，用于验证签名
- **Private Key（私钥）**：账户控制权本身，丢失 = 失去控制权，泄漏 = 别人获得控制权
  - 不截图、不上传云盘、不发给网页/AI/客服、不放代码仓库
- **Signature（签名）**：对具体消息或交易内容的授权证明，不是"登录弹窗"。签名内容必须能让人读懂
- **Merkle Tree**：用哈希把大量数据组织起来，只需少量证明就能验证某条数据属于整体

---

### 3. Wallet（钱包）

**核心认知：**
- 钱包不是"登录按钮"，而是用户管理账户、签名授权、发送交易、确认风险的入口
- 连接 ≠ 授权资产，签名 ≠ 登录，交易 ≠ 点击按钮

**三类动作及风险：**
| 动作 | 说明 | 风险 |
|------|------|------|
| 连接钱包 | 应用读取地址和网络 | 低 |
| 签名消息 | 证明控制某个地址 | 中 |
| 发送交易 | 改变链上状态 | 高 |

**关键知识点：**
- **EOA（外部账户）**：由私钥控制，最常见，但私钥丢失难恢复、权限难细分、自动化能力弱
- **Mnemonic（助记词）**：恢复钱包的高风险秘密，任何应用索要助记词都应视为危险
- **Transaction**：对链上状态的正式请求，失败通常不能撤回
- **Gas**：链上执行成本，影响费用和交易处理优先级
- **Explorer**：区块浏览器是用户查链上状态的入口

---

### 4. Smart Contract（智能合约）

**核心认知：**
- 智能合约不是"自动执行的法律合同"，而是部署在链上的程序
- 智能合约把规则变成公共基础设施，也把 bug 变成公共风险

**关键知识点：**
- **Solidity**：EVM 生态最常见的合约语言，重点理解 storage、msg.sender、modifier、event、revert
- **EVM（以太坊虚拟机）**：智能合约的执行环境，决定代码如何被部署、调用、计费
- **ABI**：应用和合约沟通的接口说明，没有 ABI 无法正确调用合约
- **最小合约示例**：状态变量 + 写操作函数 + event 日志

## Part 2：AI × Web3 Bridge（4个核心模块）

### 1. Agent Wallet（代理钱包）

**核心认知：**
- Agent Wallet 不是"给 AI 一个私钥"，而是解决：Agent 可以代表用户做哪些链上动作，这些动作有没有额度、时间、对象和风险限制

**第一性原理：**
> 控制权不能交给一个概率系统。Agent 只能拿到可验证、可限制、可撤销的行动空间。

**三条设计原则：**
1. Agent 不直接控制主资产，高风险动作要交回给人确认
2. 钱包是权限系统，表达时间、金额、合约、方法、资产、接收方和撤销条件
3. 自动化必须绑定撤销能力

**关键知识点：**
- **AA Wallet（账户抽象钱包）**：让账户拥有规则（谁操作、什么操作、何时失效、超边界怎么办）
- **Smart Account**：用合约规则承载权限、恢复和自动化

---

### 2. Machine Payment（机器支付）

**核心认知：**
- Agent 需要购买 API 调用、链上交易、数据服务、执行任务等
- Machine Payment 把"付款意图"和"实际结算"分离，为每一步提供可验证凭证

**第一性原理：**
- Agent 不应拥有无限支付能力
- 预算是执行的前提
- 报价必须可比较，收据必须可验证

**关键知识点：**
- **Stablecoin Payment**：机器支付首选，稳定币价格稳定、结算快、可编程、可验证
- **Budget（预算）**：Agent 被授权的最大支出范围，按时间、任务、服务方、金额分层
- **Quote（报价）**：包含服务内容、价格、币种、有效期

---

### 3. Settlement & Escrow（结算与托管）

**核心认知：**
- 自动化交易必须有明确完成条件，否则支付无法安全自动化
- Escrow 把资金锁定，等待交付条件满足后再释放

**第一性原理：**
> 先定义状态机，再写付款代码。

**关键知识点：**
- **Escrow**：状态机 = Created → Funded → Delivered → Accepted → Released / Refunded / Disputed
- **Receipt（收据）**：支付凭证，记录谁付给谁、金额、币种、任务 ID、时间、交易哈希
- **Delivery Proof（交付证明）**：文件 hash、API 返回日志、模型输出签名、链上 event
- **Acceptance（验收）**：用户或规则系统确认交付满足要求，高价值任务用"AI 初审 + challenge window + 人工复核"
- **Refund（退款）**：规则提前写好：谁能触发、多久可触发、是否扣费

---

### 4. Web3 Tool Use（Web3 工具调用）

**核心认知：**
- Web3 工具的风险比普通查询工具更高。读错数据误导判断，写错交易改变资产和权限
- 模型可以选择工具，但工具必须用确定性边界限制模型

**第一性原理：**
> 不要让 Agent 直接拼接任意 calldata 或调用任意地址。工具应该把危险能力封装成受限接口。

**工具分类：**
| 工具 | 风险 | 说明 |
|------|------|------|
| RPC Tool | 低-中 | 只读可宽，写入需拆分 |
| Contract Read | 低 | 调用 view/pure 函数，不改链上状态 |
| Contract Write | 高 | 必须严格模拟、权限、确认 |
| Wallet Tool | 最高 | 按连接/签名/交易/授权分不同动作 |
| Explorer Tool | 低 | 查交易、合约源码、event |

**日志原则：**
每次工具调用必须记录输入、输出、时间、来源和错误。
